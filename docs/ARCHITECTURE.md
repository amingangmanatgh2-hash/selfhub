# 🏗 معماری SelfHub v2

## چرا Webhook و نه اتصال دائمی

نسخهٔ ۱ سعی می‌کرد مثل یک ربات معمولیِ Nodejs با `mtcute` یک **سوکت خروجی دائمی** به `wss://...mtproto` باز کند و رویدادها را از همان‌جا بگیرد. روی Workers این مدل جواب نمی‌دهد:

| مسئله | توضیح |
|---|---|
| سوکت خروجی نگه داشته نمی‌شود | Durable Object فقط `ctx.acceptWebSocket()` (سوکت **ورودی** از کلاینت) را با `hibernate()` زنده نگه می‌دارد. یک `new WebSocket(...)` که خودت باز کرده‌ای با اولین request بعدی context یخ می‌کند |
| CPU محدود به هر فراخوانی | یک حلقهٔ «گوش‌دادن» که منتظر event بماند، عملاً بین requestها اجرا نمی‌شود؛ `waitUntil` هم فقط تا پایان کش شدن پاسخ و چند لحظه بعد از آن عمر می‌کند |
| تخلیهٔ ایزوله | DO بین درخواست‌ها freez/evict می‌شود؛ هر state زنده (سوکت، تایمر، بفر) از بین می‌رود |
| لاگین نصفه‌نیمه | `startLogin` یک promise معلق می‌ساخت و **بدون `ctx.waitUntil`** پاسخ را برمی‌گرداند → runtime context منقضی و جریان ورود می‌مرد. این باگ به‌تنهایی دلیل اصلی «کار ندادن» لاگین بود |

نتیجه: مدل «برنامهٔ دائمی» روی Workers ساخته نمی‌شود. پس نسخهٔ ۲ را روی تنها مدلِ قابل‌اتکای تلگرام گذاشتم: **Bot API + Webhook**. تلگرام خودش هر update را ذخیره و دوباره تحویل می‌دهد؛ اگر Worker شلوغ باشد یا پاسخ ۵۰۰ بدهی، پیام از دست نمی‌رود — و ما اصلاً لازم نیست ۲۴ ساعته بیدار بمانیم.

## نقشهٔ جریان

```
                    ┌──────────────────────────────┐
 api.telegram.org ──▶  POST /webhook/<secret>      │  Worker (src/index.ts)
                    │  ├ verify secret_token       │  بدون CPU سنگین، بدون I/O زیاد
                    │  ├ dedupe update_id          │
                    │  └ ctx.waitUntil(HUB.update) │
                    └───────────────┬──────────────┘
                                    ▼
                    ┌──────────────────────────────┐
 browser ──────────▶  /api/*  ──HMAC──▶  /internal │  HubDO (src/hub.do.ts)
   (پنل)            └──────────────────────────────┘   SQLite هم‌جا (sql)
                                    │
                     ┌──────────────┼───────────────┐
                     ▼              ▼               ▼
                engine.ts      bot.ts         logic/*
              (update → ...)  (Bot API client)  (منطق خالص و تست‌شدنی)
```

- **Worker هیچ داده‌ای ندارد.** فقط: بررسی کوکی/CSRF، بررسی رمز وب‌هوک، حذف تکراری، و فوروارد کردن به DO. یک request معمولی ≈ ۱ms CPU.
- **HubDO مغز است.** یک نمونهٔ Durable Object با `state_sql` (SQLite داخلی). یعنی تراکنش‌ها اتمیک‌اند، بدون KV/R2/D1، بدون نگرانی race بین دو request.
- **`ctx.waitUntil` همه‌جا هست** — جایی که کار پس‌زمینه (ارسال پاسخ، نوشتن آمار، sync وب‌هوک) بعد از پاسخ انجام می‌شود. این همان چیزی است که نسخهٔ ۱ جا انداخته بود.

## چرا همه‌چیز در یک DO

- ترتیب و اتمیسیته: شمارش اخطار، نردبان تنبیه، و نوشتن modlog باید در یک تراکنش باشد. DO تنها جایی است که این را دارد.
- SQLite در DO جدول‌های ساده و کوئری‌های محلی دارد؛ کوئری D1 از هر request هزینه و تاخیر اضافه می‌کرد (و rate-limit رایگان‌اش برای ربات ۲۴/۷ تنگ است).
- مقیاس: فعلاً همهٔ چت‌ها یک DO. این برای صدها گروه و هزاران پیام در روز کافی است. اگر روزی لازم شد، کلید شارد = `chat_id` و یک DO به‌ازای هر گروه — چون `HubDO` خودش هیچ state جهانی غیر از `config` ندارد، شکستنش به `chat_id` مکانیزه است.

## state در حافظه vs روی دیسک

در حافظه (بهترین‌تلاش، با هر انجماد ممکن است برود):

| چیز | چرا در حافظه مجاز است |
|---|---|
| پنجرهٔ فلود (`hist`) | یک بازهٔ ۱۰ ثانیه‌ای؛ باختنش یعنی یک پیام فلود از قلم می‌افتد، نه فاجعه |
| کش ادمین‌ها (`adminCache`) | ۱۰ دقیقه TTL؛ در بدترین حالت یک `getChatMember` اضافه می‌زند |
| بفر اطلاعیه (`pending`) | صف موقت بین فراخوانی‌ها؛ باقی‌مانده در جدول `schedule` هم قابل بازسازی است |

روی دیسک (SQLite) — چون از دست‌رفتنشان باگ امنیتی/داده‌ای است:

- هش رمز پنل + salt، و **شمارندهٔ تلاش ناموفق ورود** (نسخهٔ ۱ قفلش را در حافظه داشت؛ هر تخلیهٔ DO آن را صفر می‌کرد و limitRate بی‌اثر می‌شد)
- توکن ربات (رمزنگاری AES-GCM)، `webhook_secret`، بذر کلید
- تنظیمات چت‌ها (فقط **اختلاف** با پیش‌فرض ذخیره می‌شود: `stripDefaults` — تا پیش‌فرض‌های تازه در نسخه‌های بعد به همه چت‌ها برسند)
- keywords، notes، warns، modlog، schedule، stats_day/hour، events

## منطق خالص بیرون از I/O

```
src/logic/words.ts     نرمال‌سازی فارسی، تطبیق، فازی، لینک/دعوت، نسبت حروف بزرگ
src/logic/flood.ts     پنجرهٔ لغوا، شمارش تکرار، push کرانه‌دار
src/logic/rules.ts     decide() → تصمیم نهایی؛ warnLadder / joinBanHit / mutePlan
src/logic/settings.ts  پیش‌فرض‌ها، mergeSettings (clamp هر کلید)، canRun
src/logic/schedule.ts  parseWhen (فارسی/انگلیسی) → {at, everySec}
src/logic/stats.ts     سری‌ها، رشد، rank، CSV
```

هیچ‌کدام `env`، `fetch` یا `ctx` نمی‌بینند. به همین دلیل ۸۱ تست روی همان‌هایی که رفتار واقعی را تعریف می‌کنند اجرا می‌شود، بدون mock کردن تلگرام.

## احراز هویت پنل

```
POST /api/login  → PBKDF2-SHA256(۲۱۰k) روی stored hash → شیشهٔ قفل؟ ۵ خطا/۱۵ دقیقه (روی دیسک)
                 → Set-Cookie: sh_session=<exp>.<b64(hmac-sha256)>; HttpOnly; SameSite=Lax; Secure
هر /api/*        → بررسی امضا با crypto.subtle.verify (زمان‌ثابت) + expiry
هر نوشتن         → هدر x-selfhub: 1 لازم است (CSRF؛ فرم‌های ساده نمی‌توانند این هدر را بفرستند)
```

رمز پنل با `passwordStrength` سنجیده می‌شد؛ الگوهای رایج و نام خود محصول رد می‌شوند. توکن ربات هرگز در لاگ یا پیام خطا ظاهر نمی‌شود.

## وب‌هوک

`/webhook/<secret>` : مسیر تصادفی ۲۴ بایت هگز + همان مقدار به‌عنوان `secret_token` تلگرام (هدر `x-telegram-bot-api-secret-token`). هر دو بررسی می‌شوند؛ پاسخ همیشه ۲۰۰ است تا تلگرام update را سرکوب/تکرار نکند، و کار واقعی با `waitUntil` ادامه می‌یابد. `update_id`های تکراری در یک پنجرهٔ کوتاه کنار گذاشته می‌شوند.

## محدودیت‌هایی که در کد لحاظ شده‌اند

- `limits.cpu_ms = 30000` برای اطلاعیه و پاک‌سازی گروه‌های بزرگ
- ۴۲۹ تلگرام: خواندن `retry_after` (سقف ۳۰ ثانیه) و backoff؛ خطاهای «benign» (مثل «message to edit not found») به‌عنوان خطا گزارش نمی‌شوند
- اطلاعیه تکه‌تکه می‌شود (`broadcastMaxPerRun` + `broadcastGapMs`) و باقی‌مانده در دقیقهٔ بعد از `schedule` ادامه می‌یابد
- `text` تلگرام به ۴۰۹۶ و کپشن به ۱۰۲۴ برش می‌خورد؛ `inline_keyboard` به ۳×۸ دکمه سقف می‌خورد
- پنل بدون هیچ منبع CDN/خارجی است (فونت، JS، CSS، آیکون همه درون‌جا) تا در محیط‌های بسته و sandbox هم بالا بیاید
